Drawing on topology for this one — the branch of math concerned with which properties survive continuous deformation (stretching, bending, rearranging) and which don't.

A topologist's first move on your nav bar: your enterprise escalations and your self-serve complaints aren't actually two votes on the same thing. They're reactions to two different properties of the same object, and once you separate them you get more room to move than "we tried moving something once and got burned" suggests.

**1. Position and structure are different properties — so lock one, change the other**
Noticing: an enterprise team's daily habit is trained on a literal click location (4th item, top right, gear icon); a first-time self-serve user has no such habit — they're reading the nav cold, trying to parse what's grouped with what.
Mapping: the thing enterprise muscle memory depends on (exact position) and the thing self-serve users are struggling with (how many things there are, how they're grouped) are separable — you can hold one fixed while changing the other, the way a shape's exact coordinates and its overall structure are independent facts about it.
Move: segment nav rendering by usage habituation, not plan tier. Any account whose logs show daily touches on an item gets that item's position locked, permanently, pixel-for-pixel. Accounts below that touch-frequency threshold — which covers every new self-serve signup by definition — see the same 13 destinations collapsed into roughly 5 labeled groups. Nobody who'd escalate ever sees a single pixel move; the object a brand-new user meets is genuinely smaller.

**2. "Someone uses it daily" proves reachability, not that it needs its own slot**
Noticing: the fact that every nav item has one large account using it daily is being read as proof nothing can be cut — but that only proves each item needs to stay *reachable*, not that each needs a separate top-level position.
Mapping: two things built at different times, by different acquisitions, can still turn out to be the same destination in practice — used by the same workflows, in the same sessions — even though nothing about how they were built suggests it.
Move: pull session logs and compute, for every pair of the 13 nav items, what fraction of sessions touch both within one task window. Pairs with heavy overlap (try >40% as a first cut) become merge candidates — one item with sub-tabs, every existing URL and deep link kept alive so no bookmark or saved workflow breaks. That's likely 2-4 real merges hiding in the 13, none of them touching anyone's daily-use item.

**3. Findability is a distance problem, not a position problem**
Noticing: the settings tabs driving a quarter of your tickets are being treated as a "can't find the tab" problem — which invites the exact fix (rearrange things) that's cost you three enterprise escalations already.
Mapping: how many steps it takes to get from where a user is to where they need to be doesn't depend on any tab's position — a shortcut can shrink that distance to zero without touching the layout underneath it at all.
Move: ship a global command-palette / jump-to-setting search that indexes all 9 settings tabs and all 13 nav destinations — pure addition, zero repositioning, zero escalation risk. Track it specifically against the settings-driven quarter of ticket volume over the next two quarters. If the number doesn't move, you've learned something real: the problem was never position, and you'll have data instead of a scar to bring into the next "can we touch the nav" conversation.
