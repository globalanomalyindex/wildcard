A few outside-the-frame angles, take or leave any of them:

**1. Stop treating it as one table — think CQRS / event-sourcing split.**
What you're describing (append-only writes, slow reads, no ability to touch the read path) is exactly the shape event-sourced systems solve by *not* querying the write model. Instead of squeezing aggregation performance out of the same table the ORM writes to, you could stream the events table (via logical replication / CDC, e.g. Debezium or even native `pg_logical`) into a separate store built for aggregation — a columnar store or just a heavily-indexed replica dedicated to reporting. The nightly job and the EU morning peak stop fighting over the same rows because they're not touching the same table anymore. This also sidesteps the "ORM generates the queries" constraint entirely, since you're not trying to change what the ORM does — you're changing what it talks to.

**2. Sediment/archive framing: not all rows deserve equal treatment.**
A 900GB events table where two-thirds of the mass is history nobody mutates is a lot like geological strata or a library's active-shelf-vs-archive system — the top layer is "hot" and gets touched constantly, everything below is inert. Native declarative partitioning by time (e.g. monthly) lets autovacuum, indexes, and your 90-day queries all operate on a much smaller "hot" slice, while older partitions can be compressed, moved to cheaper storage, or just left alone since nothing ever vacuums a partition that never gets updated. It reframes the problem from "tune vacuum" to "shrink what vacuum has to look at."

**3. Autovacuum contention as a load-shifting problem, not a scheduling problem.**
Fixed maintenance windows (Sunday night only) are the same pattern electrical grids used before dynamic/off-peak pricing — a single big window instead of continuous small adjustments. Worth asking whether the actual lever is cost-based throttling rather than time-based windows: tune `autovacuum_vacuum_cost_limit`/`cost_delay` down during business hours instead of letting it run flat-out or not at all, so it does a little work continuously rather than needing a big window that inevitably collides with EU mornings. It's the same shift from "batch cleanup" to "continuous background trickle" that garbage collectors made in the JVM world decades ago (stop-the-world → concurrent/incremental).

**4. Incremental recomputation instead of recomputation from scratch.**
The 200ms → 8s creep on a 90-day rolling aggregate is the classic sign of recomputing an answer that could instead be *maintained*. This is the same insight behind spreadsheet autorecalc or materialized-view-with-incremental-refresh systems (Postgres has `REFRESH MATERIALIZED VIEW CONCURRENTLY`, or tools like TimescaleDB's continuous aggregates if that's ever on the table): instead of scanning 90 days every time a dashboard loads, maintain a rolling pre-aggregated summary that updates incrementally as new events land. It turns an O(90 days of data) query into an O(new rows since last refresh) update — and it's a layer you can insert without touching a single ORM-generated query.
