Drawing on **permutation**, viewed through a materials-science lens: how crystals encode order in the *arrangement* of their atoms rather than the atoms themselves, and how that arrangement decays, gets repaired, or gets locally re-engineered without touching the whole crystal.

Three things surfaced that seem worth handing over.

**1. Order decaying past a threshold, not degrading gradually**

In a crystal, positional order is tracked by a real, measurable order parameter that decays continuously — but the crystal's *bulk behavior* only flips once that parameter crosses a threshold, so from the outside it looks sudden even though the underlying decay was slow.

Postgres tracks something structurally identical: `pg_stats.correlation` between a column's on-disk position and its sorted value. For an append-only table it starts near 1.0 (insertion order tracks time order), and range scans on the time column ride that correlation to stay cheap, mostly-sequential I/O. As it drifts down — from vacuum reusing freed pages, from any deletes/updates scattered through the table, or just from a year of accumulated churn — the planner's cost model eventually flips from index scan to bitmap/seq scan once correlation crosses its threshold. That reads as a sudden 40x regression; it's actually a slow decay hitting a discrete flip, which fits a 200ms-to-8s creep better than most explanations.

Concrete move: before touching anything else, run `SELECT correlation FROM pg_stats WHERE tablename='events' AND attname='<your time column>';`. If it's meaningfully below 1.0, add a BRIN index on that column — a few MB even at 600GB, since it summarizes ranges instead of indexing every row, and it's built to exploit exactly this physical/time correlation rather than get hurt by its decay.

**2. Domain size, not effort, is what makes maintenance finish**

A single large crystal heals slowly because a repair-carrying defect has to migrate across a huge domain to find the damage. Refine the same material into small grains and the grain boundaries become fast escape routes — a fine-grained polycrystal anneals orders of magnitude faster than a single crystal of the same mass, purely because each repair's search domain shrank.

Autovacuum on one 600GB table is the single-crystal case: every pass sweeps a domain that keeps growing, so it structurally can't finish inside a business-hours-adjacent window and keeps falling further behind, no matter how the cost-delay knobs are tuned.

Concrete move: partition `events` by month (native declarative partitioning), then run `VACUUM FREEZE` on each partition once it goes cold and stops taking writes — a frozen, static partition needs no further autovacuum passes, so the maintenance surface shrinks to just the current and prior partition. This is plain DDL you can run through your existing connection, no infrastructure access needed from the managed provider, and you can tune `autovacuum_vacuum_cost_delay` per-partition so the hot one gets attention without disturbing frozen ones.

**3. One inserted layer changes bulk behavior without touching every atom**

Two crystals with identical composition can behave completely differently — ductile vs. brittle — purely because of one deliberately placed stacking fault: a single layer out of the normal repeating sequence. Nobody re-engineers every atom to get that; they place one plane and the bulk property changes everywhere at once.

You can't hand-tune the ORM's generated SQL call by call, but you don't need atom-by-atom control to change bulk behavior — you need one well-placed layer.

Concrete move: build a small, incrementally-maintained rollup table (hourly or daily pre-aggregates of `events`, refreshed by trigger or a lightweight periodic job as rows arrive), then repoint the aggregate reads at it by renaming — give the rollup the same table/view name your 90-day queries currently hit, so the ORM keeps emitting the same SQL but now scans thousands of rows instead of the full table. Second-order benefit: with rollups maintained continuously in small increments, there's no single multi-hour nightly recompute left that needs a fixed schedule at all — which is what's colliding with the EU morning peak in the first place.
