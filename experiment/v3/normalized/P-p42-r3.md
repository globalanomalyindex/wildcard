## angles
- Aircraft hydraulics and elevator control systems are built so that when the smart controller dies, the system falls back to hardwired mode automatically -> your bedroom light switch is currently wired *through* your automation instead of *alongside* it -> check whether your Zigbee bulbs/switches support local "always-last-state" or direct-pairing fallback so the physical switch keeps working even with the Pi unplugged

- You're rebuilding from memory each time, which means the Pi is the source of truth and single point of failure on an SD card; server operations teams gave up on lovingly-maintained machines in favor of cheap, disposable ones respawned from a definition file -> your real asset isn't the SD card but the flows and config, which can live somewhere durable and versioned -> export the Node-RED flow JSON to a git repo as a five-minute add-on next time you touch it

- You're not just facing a hardware problem but an inherited-codebase problem (inherited from yourself); the rule archaeologists and legacy-code engineers use is to figure out why something is there before removing it, because the mysterious flow is often load-bearing -> your four-hour weekend budget tempts a full rewrite, which is usually the wrong move on unclear legacy systems -> spend one weekend just annotating the existing flows with comment nodes before changing anything

- Repeated SD corruption on a Pi is a well-known symptom of unclean power (closet outlet, no surge protection, abrupt power-cycling) rather than random bad luck -> this reframes the problem from "how do I recover faster" to "why does it keep breaking," which is a much cheaper fix -> get a $10-15 UPS hat or good-quality powered USB supply, plus switch the boot drive to boot from SSD/USB instead of SD
