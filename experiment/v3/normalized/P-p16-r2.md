## angles
- Airports gate information to a personal object (boarding pass) rather than shrinking the airport; when the nav is personal rather than shared, nobody complains about size -> you have 13 items because each has heavy users, not because all users need all items -> test collapsing nav to role/usage-derived defaults (recently-used + starred) with everything else one search or "more" click away
- Restaurant menus with 21 pages avoid "bloated" complaints through categorization and hierarchy, and use a two-axis grid (popularity vs. profitability) rather than raw usage -> your "can't find anything" verbatim is a findability problem, and "usage" alone misses the difference between one whale's daily habit and what actually matters to breadth of accounts -> build a two-axis grid (% of accounts touching each item × frequency among touchers) and demote high-depth/low-breadth items to personalized/pinned space
- With 13 items and hundreds of large accounts, it's statistically near-guaranteed that some account touches each daily — this is survivorship bias (Wald's bullet holes), not proof of broad value -> "every item has heavy usage" is true almost by construction and provides no basis for permanent top-level placement -> reframe the metric from "does anyone use this daily" to "cost of one extra click for non-power-users vs. scan-tax on the 59,000 teams who never touch it"
- OSes avoid revolts over UI changes by never flipping simultaneously for everyone — new users get new defaults, power users get permanent opt-outs -> your support escalations are a rollout failure as much as a design failure, requiring two mechanisms not one redesign -> ship the simplified nav as default for new signups only first, targeting churn without touching enterprise muscle memory
