# Outside relations and working solutions — prospective protocol v1

Author: christopher robin fiore. Designed 20 September 2026. Status: development, no main result.

## Question and estimand

Does supplied outside relational information improve working JavaScript solutions beyond direct derivation, when both receive an executable conditional-rule gate and one public-feedback repair call? The primary estimand is the unweighted mean, across 32 authored task blocks, of R minus D final hidden-case success rates. A task has 256 cases, equally allocated across four regimes. Cases are repeated measurements within a task; the inferential N is 32, never 8,192 or 24,576. The task sample is curated rather than a random sample of software work. Family dependence and the single provider limit generalization.

This is a separate follow-up to transfer-v1, whose amended donor-name result is inconclusive and whose original invalid judge panel remains halted. Neither result is overwritten. Positive evidence is possible, not guaranteed. Related work already covers analogy prompting, contract synthesis, metamorphic properties and feedback-driven code repair. The scoped contribution is a controlled executable study of outside conditional laws versus directly derived rules, not a claim to have invented contracts or proved historical priority. See related-work.md.

## Conditions and system

D: derive the rule from the task. R: optionally use a matched, intact outside card. X: optionally use an intact shuffled card. All conditions receive the same task, four correct public traces and independently rejected incorrect outputs, exact response fields, source-size limits, contract gate, four-case public execution report, and mandatory final repair call. The final artifact is always the second program. A malformed first response can use this planned second call; no extra call is added. A malformed final response scores zero on every case. A delivered invalid result is never retried for quality.

The first response contains explanation, mapping, assumptions, applies, holds and program, all strings. Narrative fields together are limited to 180 whitespace-delimited words. Program source is nonempty and at most 10,000 UTF-8 bytes. Combined applies/holds source is at most 4,000 UTF-8 bytes. The final response contains only explanation (at most 180 words) and program. The strict whole-artifact validator is frozen in prompts.py.

A contract is admitted when applies executes as an input-only boolean, is true for at least one correct public example, holds executes as a boolean and is true for every applicable correct example, and at least one incorrect output is rejected while the same input is applicable. Correct and incorrect probe inputs are paired; identifiers are unique. At most eight of each are allowed. Applies and holds run in separate fresh contexts for each probe. A universal applies is legal. Rejecting a wrong output under a universal predicate is an implementation counterexample, not an applicability boundary. Admission establishes finite consistency and nonvacuity only. Public foils may expose simple type/enum errors; passing them does not establish semantic depth. Rejected rules are set aside for direct repair.

The task specification always governs. Contracts cannot change it. No extra donor search, best-of selection, hidden feedback or optional extra repair is permitted. The intervention includes supplied outside information and frozen tag matching; it does not causally isolate the checker, which all arms receive.

## Materials, matching and execution

There are eight distinct main component contracts per family: scheduling, cache/storage, synchronization and interaction state; plus two disjoint development contracts per family. Main tasks differ in required behavior rather than numeric settings alone. Task modules contain public specifications, four public examples, four regime generators, Python references, separately formulated checkers, correct JavaScript implementations and at least three named semantic faults per task. Checkers must accept correct alternative algorithms. Every required output/progress rule counts; always refusing, retaining stale state or withholding results cannot pass by merely avoiding unsafe action.

Sixteen cards contain outside facts, relation, assumptions, boundary, source links and structural tags. They contain no target IDs, code or hidden answers. A separate agent authored the card bank without access to new task/oracle files. Matching uses only public tags: greatest exact tag overlap, then SHA-256 tie order recorded in catalog.py. X uses an eight-position cyclic displacement in a frozen SHA-ordered card bank. It never equals the selected card, but may still be relevant. The bank and vocabulary are curated assistance, not an autonomous discovery claim.

The implementation receives only solve({config,state,event}), initially null state and then its own opaque JSON state. It cannot inspect later events. A legal current batch event may contain its complete batch. Expected answers, arm, task identity and hidden-case identity never enter the JavaScript interpreter. QuickJS-NG 0.16.2.1 runs in a separate Python process, with no host callbacks, module loader, I/O, ambient clock or RNG. Dates/times and randomness, when needed, are explicit task inputs. Limits: 64 MiB engine memory, 512 KiB stack, 0.05 CPU seconds per engine entry, 0.2 cumulative CPU seconds per trace, fresh context each trace, 120 worker CPU seconds and 180 worker wall seconds. Maximum 64 events, depth 48 (returned step object at depth zero), 131,072 serialized characters per step and 262,144 UTF-8 output bytes per trace. Values are dense arrays/plain enumerable own-data objects and finite JSON primitives; no cycles, accessors, symbols or custom prototypes/hooks. These are containment limits, not speed measurements or a certified native-engine security boundary.

Syntax errors, execution exceptions, source/shape limits or per-candidate execution limits make the affected case fail. Infrastructure failure of the worker halts evaluation rather than being silently scored as a candidate failure. All output records remain available. Instrumentation defects require a visible version or amendment, never quiet rescoring under changed rules.

## Acquisition and masking

Requested generator: gpt-6-astra, low reasoning, isolated Codex CLI. The transport records requested alias, CLI version, exact prompts, raw events, response, validation outcome, attempts, times and observed token usage. Returned immutable model snapshot, temperature, top-p, output-token cap and sampling seed are not exposed and are reported as unknown. Same-provider evaluation here is deterministic host execution, not a second model judge. Matching is by logical calls, response limits and feedback opportunity, not exact tokens, context lengths or hidden model compute. The authenticated subscription's marginal USD cost is unavailable.

The model working directory is empty. User config, repository instructions, tools, shell, web search, apps, plugins, memories and multi-agent access are disabled for these calls. Public text is the only input. At most two transport attempts are allowed only when no turn.completed event is observed. Exact stdout and stderr bytes are saved before parsing; malformed non-object events or items are counted, and UTF-8 parsing replaces incomplete or invalid byte sequences without changing the saved bytes. A completed invalid JSON/schema response is retained without retry. A completed turn accompanied by a nonzero CLI exit preserves its delivered response, is an acquisition integrity failure, and is never resampled. Tool use is also an integrity failure. Interrupted partial attempts require a visible ledger adjudication; resume verifies existing records and never overwrites them. Request sidecars and the complete attempt-file inventory are validated. New acquisition is prohibited after a final-program seal or hidden reveal; initial acquisition is prohibited after the final manifest.

Initial requests use a deterministic SHA schedule. Complete all initial calls before deriving final requests. Each final prompt receives only its own first artifact, its public contract report and own four public execution reports. Observed output is included only when its canonical encoding is at most 4,000 UTF-8 bytes; otherwise include count, SHA-256 and a uniform omission reason. All case statuses, up to 16 checker violations and runtime error remain visible. Invalid initial response text is limited to its first 12,000 UTF-8 bytes, dropping an incomplete terminal code point. Final requests use their own frozen SHA schedule. The public gate and feedback construction are identical across arms.

Commit and publicly push source snapshots, all prompts, schemas, task/card assignments and initial manifest before initial calls. Commit/push the entire initial panel and derived final manifest before final calls. Commit/push every final program and seal before revealing any hidden cases. Git history uses merge commits to preserve this sequence. Phase gates verify that every required artifact is tracked, unchanged and present at the published current commit. Initial prompts, card matching and schedules are reconstructed from frozen public sources; final prompts are reconstructed from each recorded initial artifact and its frozen public feedback. Prior calibration is revalidated using its frozen analysis implementation, and its manifest and results hashes are bound into the next cohort manifest.

The main hidden seed is 32 operating-system-random bytes, kept outside the repository and model working directory. Publish SHA-256 of its lowercase hexadecimal representation in the manifest. After every final artifact is sealed and pushed, reveal the seed and generate exactly 64 cases per task per regime, using the frozen SHA derivation and Python generators. Ordinary, boundary, adversarial and within-contract distribution-shift semantics are documented per task. Validate every hidden reference against its checker before executing any candidate. Preserve the full corpus, per-event outputs, violations and final scores. This separation prevents adapting implementations to hidden outcomes; it does not establish real-world contamination freedom for familiar software concepts.

## Development gate

At most two development rounds are permitted. Each round runs eight disjoint development tasks, three arms and two calls: 48 logical calls. Development validates transport, strict schema, runtime, public feedback and benchmark instrumentation. Difficulty decisions use D only. D mean hidden success <=0.10 is a floor; >=0.95 is a ceiling. If either holds, do not start main acquisition under that configuration. One declared revision may follow round one, preserving all original artifacts and documenting its reason before round two. Revision may strengthen benchmark task interactions or select an explicitly disclosed fixed generator configuration using D failures, but never choose changes by the observed R−D difference. If the second round remains unsuitable, publish a halted calibration outcome and an executable system without pretending to have run a confirmatory main test.

Development tasks should resemble the kind of contract interactions in main while remaining different contracts. Distinct simple smoke tasks alone are insufficient evidence that the main benchmark is discriminating. Oracle defects, untestable requirements, material public-spec ambiguity or invalid task independence block main collection until corrected and revalidated. No main outcome is a tuning signal. Main has exactly 192 planned logical calls; once begun, complete the fixed sample regardless of direction. Do not expand N or remove difficult tasks based on results.

## Outcomes and inference

A hidden case passes only if execution succeeds and the independent task checker accepts every required per-event output. Each final program's primary score is the number of passing cases divided by 256, equal weight across regimes. Report all-suite acceptance (256/256) separately, plus family/regime scores, admission rates, first-stage public pass rates, schema/runtime failures, wall times and all-attempt token usage. No case-level confidence intervals are presented as if cases were independent tasks.

Primary R−D: 100,000 paired task bootstrap samples, resampling tasks within each of four families and retaining the observed family weights. Report the percentile 95% interval. Use a two-sided mean paired sign-flip test with 1,000,000 draws and a plus-one numerator/denominator correction. Exact seeds and SHA-counter PRNG are frozen in analyze.mjs. Work in integer pass-count differences until division to avoid float ties. Sign flips require symmetric/exchangeable paired differences under the null; the fixed task set and family structure limit that interpretation. Bootstrap intervals characterize resampling these task blocks, not a representative population guarantee.

Directional positive evidence requires positive mean, interval lower endpoint >0 and p<=.05. Practical-benefit status additionally requires a point estimate >=0.10. This does not establish a true minimum ten-point effect. Test R−X inferentially only when the primary directional gate passes, using the same method in a fixed sequence. Otherwise report its observed difference descriptively with no confirmatory claim. Other outcomes are descriptive. A non-significant result is not equivalence; ceiling/floor patterns remain visible.

The chosen N has limited power: an exact whole-program binary illustration at N=32 has about 33.4% power for a 20-point advantage with discordance probabilities .30/.10, and 62.5% for a 30-point advantage at .40/.10. This illustration is not a power guarantee for the continuous primary score. It motivates honest uncertainty rather than optional enlargement.

A separate benchmark-only prototype gate is R mean >=.95 and at least 24/32 R programs passing their full suites. Passing this gate does not establish an R−D benefit, production reliability, visual taste, security or deployment readiness. Any broader release remains a research prototype. Findings are published whether favorable, unfavorable or inconclusive.
