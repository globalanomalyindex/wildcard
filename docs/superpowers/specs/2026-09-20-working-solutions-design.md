## Selected mechanism

Use **outside-derived conditional contracts**. The generator receives the complete target task and may use a source-backed outside relation to derive an applicability predicate, a behavioral property, and a target implementation. A host checker tests the proposed contract against the same public correct examples and incorrect examples available to all conditions. A contract is admitted only if it is executable, holds for every applicable correct example, applies to at least one correct example, and rejects at least one incorrect example under the same input. The applicability predicate reads only the input, so it cannot avoid a bad output after seeing it.

A universal predicate is allowed. Its rejected incorrect example is an implementation counterexample, not an invented failure of applicability. Conditional predicates additionally expose which public inputs lie outside the proposed rule. Passing this small gate means consistent and nonvacuous on the public examples; it does not prove the property or its source-to-target mapping universally valid. The target specification always outranks the proposed contract. A rejected contract triggers direct repair, not task abandonment.

The direct comparator derives the identical contract fields from the task itself and receives the identical checker, public examples and repair opportunity. The only primary intervention is supplied outside information and its frozen matching process. A third condition receives an intact, shuffled card. The study does not isolate the checker as a causal component because all conditions use it.

This differs from the alternative of appending a metaphor without checking its operational content. A search over many donors or candidate implementations is deferred because extra search would confound the initial test. Related work already establishes analogy prompting, metamorphic testing, specification synthesis and counterexample-guided repair. The scoped contribution is the outside applicability representation and its controlled executable evaluation, not those underlying techniques.

## Interface and execution

Each solution is a synchronous JavaScript function `solve({config, state, event})` returning `{state, output}`. The host starts with null state, supplies one event at a time, retains opaque JSON state, and records each task-defined output. Future events are never supplied to the implementation. A batch task may expose a complete batch within its current event when its contract permits that information. No network, filesystem, module imports, clocks or ambient randomness are needed; all observable time and input arrive explicitly. Candidate code and contract functions run in a separate, bounded JavaScript interpreter process with no host callbacks or I/O bindings. The evaluator and expected outputs remain outside that process. Memory, stack, execution time, source size and output size are bounded and tested before acquisition.

The response schema carries the complete program, a bounded explanation, mapping/assumptions, input-only applicability source and input/output property source. Exact limits and schemas are frozen in the protocol after development validation. Every delivered output is retained. The first call proposes a contract and implementation. The second mandatory call receives the same task, its own first artifact, the contract-gate report and a fixed-format public execution report, then returns the final implementation. Score the second artifact even if the first was better. Malformed first artifacts may be repaired in this common second call; malformed final artifacts score zero.

## Benchmark and controls

Author 32 distinct task blocks, eight each in scheduling, storage/cache, synchronization and interaction state, plus eight disjoint development tasks. A task is a different component contract, not a renamed numeric variant. Related family structure remains a limit on generalization. Each task must define complete legal behavior, four correct public fixtures, independently validated incorrect foils, and a donor-blind evaluator. Correct alternative algorithms must pass. Liveness and progress requirements prevent always-refuse or never-update solutions from appearing correct.

The main conditions are D (direct contract), R (matched outside contract), and X (shuffled outside contract). Each gets two model calls, identical response limits, identical public execution opportunity and one final artifact. Thus the planned main acquisition is 192 logical calls. This matches calls, output contracts and feedback opportunities, not actual tokens or unavailable decoding settings. Use the recorded isolated text-only Codex transport; preserve requested aliases and unknown provider-returned snapshots honestly.

A source card contains donor facts, assumptions, a failure boundary and primary-source citations. It cannot contain target-specific code, task IDs, hidden test values or answers. The matcher uses only public structural task features and a frozen card index. A curated assignment is explicitly curated assistance, not autonomous discovery. Shuffling preserves whole cards and uses a frozen permutation.

The primary outcome is each task's mean correctly solved hidden-instance rate over four equally weighted regimes: ordinary, boundary, adversarial combinations and a specified within-contract distribution shift. There are 64 cases per regime. Every case requires legal execution and all mandatory behavioral and progress requirements. Hidden case counts do not inflate the independent N beyond 32 task blocks. Full-suite program acceptance is reported separately.

Before main generation, freeze the task specifications, generators, reference/checker code, scoring, protocol, prompts, card matching, run schedule, runtime dependencies and analysis. Validate known-correct implementations and named requirement-breaking mutants. Commit a private hidden-seed hash before collection; keep the seed and all oracle access outside model contexts. Reveal and materialize the complete main corpus only after all final programs are immutable. Public examples are the only feedback during solving.

## Development and decision rules

Development checks format, execution isolation, oracle validity and baseline difficulty on separate tasks. Permit at most two declared development rounds. Any global difficulty revision is chosen from D alone, never by searching for an R advantage. Keep every version and outcome. If the evaluator is invalid or D remains at floor/ceiling, halt before main acquisition and state that the benchmark is not ready. Main outcomes must not be used to tune this run.

Register one primary R−D contrast, paired by task. Use a within-family task bootstrap interval and a paired sign-flip test with frozen seeds; document the symmetry/exchangeability assumptions. Positive directional evidence requires a positive estimate, p <= .05 and the 95% interval above zero. A practical-benefit decision additionally requires a point improvement of at least 0.10. This does not prove a true minimum ten-point gain. Test R−X only after the primary statistical gate succeeds; other breakdowns are descriptive. A non-significant result is not equivalence.

This sample is a bounded benchmark, with limited power for modest gains. Complete the fixed sample regardless of direction. No optional expansion, best-of artifact selection, hidden-result feedback or post-hoc removal of difficult tasks. A defect requires a visible amendment with the original evidence preserved. Benchmark gains alone do not establish production reliability or improvement in visual taste.
